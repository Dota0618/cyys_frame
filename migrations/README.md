# 当前迁移设计与操作边界

本文记录数据库结构、关联校验及升级边界。Phase 3 的实现和 G1 证据见 [验收记录](../docs/migration/phase3-acceptance.md)。

## 唯一执行入口与资源

由业务应用中的 Flyway 执行，默认加载 `classpath:db/migration`。构建只将本目录 system/business 中的版本 SQL 打进 JAR；不包含 dev-data。使用一个 schema history，不按功能另建迁移引擎。

- V1：已执行的空库系统结构，历史内容和校验值保持不变。
- V2：保留给本地身份初始化，文件在 dev-data，默认不加载。需要时由同一个 Flyway 显式添加该文件系统位置。
- V3：移除 V1 的全部数据库外键；增加部门版本和唯一键、成员部门字段、规范化角色部门范围及数据操作审计。最终结构没有外键。
- V4：成员关系增加本单位 display_name、version 和创建时间索引；初次从全局昵称/姓名/登录名回填，此后的单位编辑不改全局资料。
- V5：角色增加 version，角色基本信息、菜单授权和自定义部门范围作为一个受版本保护的事务更新。
- V6：菜单增加 version，共享菜单基本信息和状态修改使用乐观版本边界；平台关键权限的停用另受最终管理员事务保护。
- V7：新增全局通用配置 sys_configure、字典分类 param_basic 与字典项 param_basic_type；保留旧表业务字段，增加版本、审计和唯一约束。2026-09-15 已在现有 cyys_frame 执行成功，专项及后端全量回归通过；两个新管理页面的 [真实浏览器验收](../docs/migration/phase4-2-global-acceptance.md) 已完成。
- V8：新增最小登录记录 sys_login_audit，保存账号、可选账号主键、服务端核验的单位、IP、结果、必要原因和时间；不保存密码、令牌或原始请求参数。未知账号或无法确认单位归属时保存空单位，不使用请求参数冒充归属。2026-09-20 已在现有 cyys_frame 执行成功，审计 HTTP 和浏览器验收已通过。
- V9：新增私有文件 sys_file_entry 和持久化分片 sys_file_part；服务端生成位置、单位和操作者，支持小文件直传及本地断点续传。
- V10/V11：文件表连接字段与现有身份/部门表的字符规则对齐。V10 修正本地差异；V11 跟随 sys_org 的实际规则，避免假设其他部署也使用 general_ci。已执行版本保持不变，采用前向迁移。
- V12：新增个人文件目录 sys_file_dir，文件增加 dir_id，扩展 PURGING/PURGED 清理状态；目录跟随现有文件表字符规则，无外键。删除目录将完整授权的文件移回默认目录；回收恢复和永久清理分别授权。
- V13：文件增加临时清理完成时间、失败重试时间及候选索引；为此前未登记期限的直传 UPLOADING 补充创建后一小时期限。后台到期先标 FAILED，再删除登记临时对象；READY 主文件保留。
- V14：组织通知 `sys_org_notice`、首次阅读关系 `sys_org_notice_ref` 及有序文件引用 `sys_file_binding`；新表排序规则跟随 sys_org，不建立外键，不写入默认通知或字典数据。
- V15：平台共享系统通知 `sys_notice`，无单位字段、无阅读关系；标题、类型、纯文本正文及是否显示，保留版本和审计。不写默认字典或通知数据。
- V16（已编写，尚未执行）：平台版本更新 `sys_version`；文件关联增加源单位 `file_scope_id`，既有 V14 关系按原单位回填。父业务范围、源单位和资源组合受约束，引用保护使用源单位查找全部关系。
- V17（已编写，尚未执行）：全局地区参数 `param_region`，保留父级、编码、名称、简称、邮编、经纬度、层级与排序。唯一编码包含软删除历史；下级是否存在由索引查询计算，不维护易失真的 has_child 冗余字段。
- V18（已编写，尚未执行）：`sys_serial_rule` 和 `sys_serial_counter`，保存单位/业务固定规则及分周期计数；数据库唯一键与事务锁支持并发预留，不导入旧全局计数、不创建默认业务规则。
- 后续正式迁移从 V19 递增，system/business 共用版本序列。
- 测试单位由测试配置在正式迁移之后准备、测试类结束时清理，不占用版本号、不留下测试迁移历史。

`baseline-on-migrate=false`、`clean-disabled=true`、`validate-on-migrate=true` 防止把未核对的旧库自动当成新基线。V1 在本次调整前尚未接入版本迁移权威；改造前内容已保存到本地源码快照。不要拿新 V1 覆盖某个已有迁移历史的已部署库。

## 首次本地运行

先核对现有 MySQL 中明确选择的数据库及其迁移历史，再注入连接配置。空 schema 执行正式 V1、V3–V18（V2 仅为可选本地初始化）；含旧表或业务数据的 schema 需要先制定对应升级脚本，不能删表重建或自动 baseline。使用 MySQL 8、InnoDB、utf8mb4，排序规则按部署约定统一。没有内置默认账号或密码。V16–V18 当前仅编写，运行结果以实际进度为准。

需要本地初始身份时，在首次空库迁移前，于被版本控制忽略的外部 application-local.yml 中显式增加：

```yaml
spring:
  flyway:
    locations:
      - classpath:db/migration
      - filesystem:F:/git/frame/cyys-framework/migrations/dev-data
    placeholders:
      bootstrapScopeId: unit-default
      bootstrapAccountId: local-admin
      bootstrapLoginName: local-admin
      bootstrapPasswordHash: "<自行生成的有效 BCrypt 散列>"
cyys:
  data-isolation:
    mode: single
    single-scope-id: unit-default
```

该文件还需提供数据库连接参数；显式激活 local profile 或指定外部配置位置。四个占位符缺少任一个，Flyway 都应停止；不要把示例占位文字直接作为密码散列使用，也不要把这份本地配置提交到版本库。

V2 仅创建一个实际成员关系和一项显式平台单位访问权限，不创建通用管理 CRUD 权限。生产环境不得加载 dev-data，生产初始管理员应由部署流程提供受控的身份数据并独立验收。身份初始化后，single 启动校验要求其单位主键存在且启用。

V2 在本地首次初始化时按 V1 → V2 → V3 顺序执行。已经到 V3 的库不会自动补执行较小版本 V2；不得为补种子开启全局乱序迁移。此时应另行准备受控的身份初始化事务。当前 cyys_frame 没有实际使用账号，不能把测试账号当作本地管理员。

## 当前表归属

| 表 | 分类与边界 |
|---|---|
| sys_user | 全局账号，身份查询受控；不会直接作为接口输入输出 |
| sys_scope | 受保护的平台单位目录 |
| sys_menu | 受保护的共享菜单/权限定义；type=1/2/3，编码和类型创建后不可变，平台专用权限不能由单位角色生效 |
| sys_user_scope | 单位成员关系；读取同时检查账号、单位、成员状态及有效期 |
| sys_role | GLOBAL 平台角色或具体单位角色；GLOBAL 不是业务数据拥有者 |
| sys_user_role | 授权关系与被授予角色必须同 scope_id；由 RoleGrantService 写入校验和读取条件共同保证 |
| sys_role_menu | 通过角色决定授权所属范围，不伪造独立业务单位 |
| sys_org | 单位内部门，归属不等于独立单位；leader_id 关联全局用户 ID，写入时校验其为本单位有效成员 |
| sys_role_org | 自定义部门范围；role_id、org_id 对应角色和部门，scope_id 必须同时匹配两者，读取拒绝错配 |
| sys_data_audit | 成功写入事件；真实 actor_id、scope_id 和 resource/record_id 由业务服务填写，与业务一起提交或回滚 |
| sys_login_audit | 登录结果记录；失败时 user_id/scope_id 可为空，读取按当前单位及独立登录记录权限限制 |
| sys_configure | 全局业务配置，name 唯一，value 可为 null 或空字符串；type=1 系统参数、2 第三方接口业务参数 |
| param_basic | 全局字典分类；沿用用户输入的数字字符串 id，system_name 全局唯一 |
| param_basic_type | 全局字典项；basic_id 关联分类，param_key 在该分类内唯一，param_value 是显示值 |

关联关系只在文档中声明：成员关联 user/scope；授权关联 user/role/scope；角色菜单关联 role/menu；部门关联 scope 及同单位父部门；成员 org_id 和角色部门范围关联同单位部门。部门删除检查子部门、成员及角色范围引用；单位及平台角色删除拒绝仍有账号授权；菜单删除拒绝子节点及角色引用，均不依赖数据库级联。GLOBAL 账号授权只替换目标账号的 GLOBAL 关系，保留全部单位角色。

可用平台管理员定义为：启用账号持有启用 GLOBAL 角色，该角色关联启用、type=3、platform_only=1 的 `platform:scope:access` 权限。可能减少该集合的菜单、平台角色或 GLOBAL 账号授权写入，先锁定关键权限行，写入后以锁定式当前读确认至少剩余一人；不满足时整个事务回滚。所有平台管理操作还需对应的 `menu:*` 或 `platform:role:*` GLOBAL 权限，前端可见性不替代服务端检查。

登录名全局唯一。角色编码在 scope 内唯一。成员和授权关联保留业务唯一键：软删除后需要恢复原关系，不通过重新插入相同关系绕开冲突。多个有效默认单位会被身份解析拒绝，后续成员写服务仍需保证最多一个有效默认值。

成员管理使用 sys_user_scope.id 作为页面记录 ID，user_id 由服务端解析。新增流程在同一事务创建全局账号和当前单位成员；已有账号加入另一单位尚无公开入口。编辑只改 display_name、org_id、status，带 version 处理并发；单位归属、账号、密码、默认单位和成员身份不由编辑表单修改。角色操作只替换当前单位的授予记录，保留其他单位和 GLOBAL 授予。

部门负责人使用 sys_org.leader_id 保存全局用户 ID。候选仅返回当前部门新增或修改操作可用的本单位有效成员，保存时在事务内重新校验并锁定成员关系；已有负责人后来失效时允许原值随其他字段修改继续保留，页面以禁用历史项回显，但不能重新选择该失效成员。部门删除不删除用户或成员关系。

## 全局配置与字典（V7）

- 三张表均无单位字段。配置和字典管理要求 GLOBAL 的 `platform:scope:access` 及对应 `configuration:read/create/update/delete` 或 `dictionary:read/create/update/delete` 权限，选择业务单位不改变这些数据的归属。
- 保留旧工程的 name/value/type/desp/sort、name/system_name/sort、basic_id/param_key/param_value/desp/sort；配置类别在 API 中使用 SYSTEM/THIRD_PARTY 枚举。配置及字典项 ID 由服务端生成，分类编号仍由用户输入，按字符串传输以避免大数字精度损失。
- 配置名称、分类编号/内部名称、项编码在创建后不可修改，避免业务保存的引用失效。修改命令只包含可编辑字段及 version；归属、审计和新记录版本由服务端填写。
- 配置修改采用完整替换语义，value 字段必须出现；null 表示未设置，空字符串表示明确空值，文本 `0`、`false` 原样保存。配置不存在返回 404，存在且 value=null 的记录仍返回显式 null；不通过真假判断替换默认值。前端清空已经填写的输入会提交空字符串。
- 字典与项按原功能 sort、id 升序；页大小上限 200。分类删除先锁定分类，再以锁定式当前读检查剩余有效项；所有项写入也锁定同一分类，阻止与分类删除并发产生孤立项。项修改/删除同时限定 basic_id、id、version。
- 删除采用软删除；唯一键覆盖历史记录，编码不能靠删除后重建重新赋予另一含义。未建立回收恢复入口；未来真实业务字段需要回显历史值时再接入受控选择器，不以管理分页接口替代该能力。
- 当前管理查询直接读取数据库，没有单位缓存、反射刷新或手工重建缓存入口。后续若有真实缓存消费者，按这三张表的全局属性选择缓存范围；现有单位用户名称缓存保持其自身范围。
- 这张通用配置表不作为 Spring 部署配置或认证配置源。数据库连接、认证密钥、令牌、密码等由外部配置管理；第三方类别只保存非敏感业务参数。没有复制旧库配置值、密钥或默认账号；旧数据导入须先区分业务参数与部署/安全参数。
- 此次 V7 面向受管的新结构，不是对原库的自动导入脚本。旧 is_delete、date_create/date_update 等字段需在专门导入方案中映射为 deleted、created_at/updated_at，并预检重复内部名称、重复项编码和孤立 basic_id。

## 私有文件与断点续传（V9–V11）

文件元数据使用受保护 Mapper，按当前操作的单位、部门/本人范围查权；下载另需 `file:content:read`。分片关系采用文件、单位和上传者完整限定，操作前必须先锁定并授权父文件。上传归属来自当前有效成员部门；部门删除同时检查有效文件引用，不允许客户端传入拥有者、存储地址或对象键。

上传任务先登记不可变的存储配置、对象键、预期长度、每片 SHA-256 和七天有效期；每片写入和合并都核对当前权限。文件行锁串行化同一任务的分片、完成、取消；重复已确认分片/完成幂等。合并重新校验全部分片，损坏片退回待补传并返回 422；完整结果确认后才记 UPLOAD 审计。磁盘和数据库不能原子提交，崩溃对象仍有元数据，续传重试只处理登记键。

删除是逻辑删除：禁止下载，保留完成的主文件；临时分片清理失败会明确返回错误。取消先标 FAILED，再清理，失败可重试。V12 增加个人目录、完整批次移动/删除及回收恢复；永久清理先提交 PURGING，再删除登记对象，全部完成后提交 PURGED 和成功审计，失败保留待清理记录供重试。七天过期禁止继续上传，可取消清理；V13 后台按固定单位、有界批次清理过期上传及直传崩溃遗留，失败延后重试；V14 组织通知接入附件关联和引用保护，预览及其他业务消费仍待后续切片。云模式仍只有配置契约，没有外部 API 调用。

## 组织通知与附件（V14）

组织通知归属当前单位及创建时选择的授权部门，后续不得修改归属；标题、正文、可空类型及有序附件在同一事务保存，保存即可查看，不增加旧工程没有的发布开关。类型使用全局 `NOTICE_TYPE` 字典，保留已失效历史编码和标签，不自动生成默认分类。编辑不清除首次阅读记录；阅读关系以单位、通知、真实用户为唯一键，首次时间由数据库保存，名单查询使用独立 `org-notice:receipts:read`。

`sys_file_binding` 显式保存单位、登记资源、父记录和文件 ID，以 sort 保存顺序；当前登记资源只有 ORG_NOTICE。绑定及文件删除协调同一文件锁；新关联复核可选范围和 READY 状态，已有引用禁止逻辑删除/永久清理。删除通知或移除附件仅解除关联；授权通知阅读者可通过父通知入口下载，不要求文件管理权限。关系无外键，由服务事务和唯一约束维护；组织删除同时检查有效通知引用。

## 旧数据与模式切换

### 地区参数（V17，待运行验收）

管理使用 GLOBAL `region:read/create/update/delete`，每级分页加载，不假设只有中国根节点。沿用旧页面父级创建后不可改；level 由父级加一，根节点为 0。新增子节点先锁父级；删除检查真实下级并与新增协调，批次任一版本/下级冲突则全部回滚。编码可按旧页面修改，但不能复用现存或历史编码；业务引用接入时需补相应校验。

经纬度从旧 varchar(20) 改为有范围校验的 decimal（最多 15 位小数）；旧字符串须预检空值、格式、范围与精度后导入，不能静默截断。名称/简称/编码各保留最多 20 字符，邮编最多 6 字符。没有导入旧 SQL 中的地区样本或生成静态 JS；全量旧数据和地区导出、业务选择器缓存另行验收。

### 系统通知（V15）

版本更新 V16 同样为全局内容；旧业务 `version` 映射 `release_number`（最多 10 字符），旧 date_update 保留日期语义，content 最多 1000 字符，类型为 `VERSION_TYPE`。`version` 新字段只用于并发控制；旧附件字符串须另行导入显式关联，不能把旧 URL 当作新文件 ID。当前源码完成，V16 运行及迁移验收尚未执行。

`sys_notice` 保留旧 title/type/content/is_show 语义；类型来自 `SYSTEM_NOTICE_TYPE`，标题最多 100、正文最多 2000 个字符，API 以 visible 布尔值表达是否显示。新增默认隐藏；修改必须显式提交显示状态与版本。历史失效类型允许原记录保留，不能新选；标签批量查询并保留创建/改选时的备份。管理接口为 `/api/admin/platform/system-notices`，必须有 GLOBAL `platform:scope:access` 和相应 `system-notice:read/create/update/delete`，同名单位权限不能维护平台内容。切换单位不改变内容归属，操作审计记 GLOBAL。

按用户最新要求，不建立系统通知阅读表、已读状态、回执或专门阅读流程。当前只接入平台管理页面，尚无其他内容展示消费者；后续消费入口需单独明确认证与显示过滤。旧数据导入仍需预检类型编码及 is_show 的真实旧值，不将任意字符串默认为 true。单位通知后续开发暂停，V14 已执行历史保持原样。

现有 cyys_frame 已执行正式 V1、V3、V4、V5、V6、V7、V8、V9、V10、V11、V12、V13、V14；没有向只读旧框架数据库写入。旧组织样本的显式归属转换已在同库专属测试表演练。完整旧库的登录名冲突、旧密码、单位归属、主子关系、附件/回收数据仍需逐项盘点；不明确的归属隔离待处理，不能默认写入某个单位。

旧库升级需要独立的版本脚本和核对报告，包含数据量、重复键、错配角色、孤立关联与回滚路径。本次不通过删除旧数据证明新结构可用，也不自动修复旧库数据。

V3 在移除外键前检查旧自定义部门串和范围值。非空 custom_orgs 需要独立升级方案，保存并核对明确的 role/scope/org 映射；本版不自动转换非空旧串，不能清空原字段以跳过检查。MySQL DDL 不保证整个版本原子回滚，正式升级前备份并预检；失败后按已执行语句核对，不直接 repair 掩盖失败。

模式变更采取停机调整：先停止实例、保留原归属数据、统一部署配置，再启动并重新登录。当前会话为进程内存，重启后失效；无运行任务传播机制，也没有热切换功能。single/multi 切换不会移动或合并数据。

## 验证范围

自动测试只使用 MySQL，通过 `CYYS_TEST_DB_URL/USERNAME/PASSWORD` 指向明确选定的现有测试 schema，不自动创建数据库。使用正式 V1/V3/V4/V5/V6/V7/V8/V9/V10/V11/V12/V13/V14、实际 Mapper、HTTP 和 Redis 验证。MySqlTestDatabaseGuard 在应用刷新及 Flyway 之前检查目标：只接受空 schema 或本套测试已初始化且不含业务数据的 schema。不会清空用户数据库；不明残留拒绝自动处理。

结构和旧样本演练在同一库的专属 `g1_mig_` 表执行：仅给正式 SQL 的对象名加测试前缀，专属历史从 0 起步，覆盖空结构 V1/V3、显式 V1/V2/V3、代表性组织样本和失败反例。开始前拒绝覆盖已有同名前缀表，结束后只移除本例创建的表；不修改正式迁移历史，不调用 Flyway.clean。实际结果见 [改造进度](../docs/migration/progress.md)。

接入机制核对依据：[Spring Boot 数据库初始化说明](https://docs.spring.io/spring-boot/how-to/data-initialization.html)、[Sa-Token 配置说明](https://github.com/dromara/Sa-Token/blob/dev/sa-token-doc/use/config.md)。这些资料说明框架机制，不代替本项目的行为验收。
